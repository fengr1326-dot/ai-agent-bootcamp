# 实施状态与验收边界

更新：2026-09-19。依据产品设计文档及 `technical-solution.md` 实现。

## 当前结论

已有可运行的开发后端与原生 iOS 客户端源码，覆盖主要饮食记录闭环；**不是完成上线验收的产品**。后端已实际启动并执行 HTTP 流程测试，iOS 尚未在 Xcode 编译。Windows 没有 Xcode / iOS Simulator / Docker；已用项目级 PostgreSQL 17 补做真实数据库联调，Redis、真机和供应商联调仍未完成。

最近一次本机验证：TypeScript 构建通过，普通验证 82 项通过、6 项依赖外部服务的测试跳过；另以临时真实 PostgreSQL 运行其中 5 项并全部通过，剩余 1 项 Redis 测试待执行。共 87 项独立测试已实际通过。Swift 源码通过便携语法检查，但没有 Apple SDK 类型检查；依赖安装审计为 0 项已知漏洞。构建产物独立进程启动、健康检查和账号写入已验证。

## 与原方案的阶段性差异

1. 食物目录只有 12 个开发样本、5 个组合，所有响应带实验标记和来源版本；不是已授权的正式营养数据库。无法覆盖常见混合菜、烹饪方法和真实餐厅菜品。
2. 个性化目标是开发系数，不是已通过临床或营养专业审核的目标。`NODE_ENV=production` 有硬性发布阻断，不能仅改个环境变量就作为正式健康产品发布。
3. 数据库使用每账号一个 JSONB 聚合保存原子状态，尚未拆为方案中的多张关系表。适合开发阶段，未进行负载、备份恢复和大规模历史数据验证。
4. Swift 的路径/方法绑定自动生成；值模型由手工维护和共享样本验证，目前不是完整 OpenAPI 自动生成 SDK。接口破坏性变化仍需审阅，CI 的一致性检测不等于跨历史版本兼容性验证。
5. 目前使用本地系统通知，没有实际 APNs 远程推送发送器；App 恢复时同步权威状态。跨设备后台取消和送达回执尚未实现。到期本地计划保守计入每日上限，并不冒充已确认送达。
6. 未实现线上可观测性平台、供应商评测集、常吃组合学习、备用 AI 供应商、条码/OCR 辅助、HealthKit。HealthKit 本来就是后续阶段。
7. 真实视觉 API、S3、Apple 登录尚未配置凭据。当前测试中的供应商是明确的模拟服务，不能作为真实识别准确率证据。
8. 照片保留期限尚未获得用户确认，自动永久删除方案被安全检查拒绝，**没有创建或启用自动照片清理任务**。目前账号删除会先删除对象再移除账号，失败保留重试路径；原图单独管理与供应商端删除回执仍需补齐。默认不授予模型改进用途；供应商训练禁用必须另外核查。
9. 用户数据导出当前是同步 JSON，不含令牌、设备推送标识和幂等缓存；尚无异步大规模导出和备份清理服务。

## 已采取的数据保护

- 私有数据按账号隔离，刷新令牌服务端只保存哈希；写操作要求幂等 key。
- 照片只使用短时私有上传地址，上传前与供应商发送前分别重新编码，不把定位元数据传给视觉服务。
- 网络日志不记录身份令牌、餐次正文、照片或身体信息；错误不返回堆栈。
- iOS 本地缓存禁止 iCloud 备份并设置文件保护；会话只存设备 Keychain。正式发布仍需真机检查 SQLite 辅助文件保护和恢复流程。
- 未成年及特殊健康情形不提供个性化营养目标。
- 禁止把“推测的识别结果”作为已吃事实写入；识别失败不产生伪造食物。

## 上线前必须完成

- 在 Mac 编译并修复所有 Swift 6 类型/并发检查问题，执行 XCTest、XCUITest 和至少一台真机的相机/弱网/通知/权限测试。
- 在隔离服务上执行 Redis 重试测试，以及 Docker 构建和恢复演练。PostgreSQL 迁移与事务冲突已通过本机临时实例验证，备份恢复和负载测试仍待完成。
- 选择有许可的营养数据和专业审核负责人；审核目标区间、安全边界、过敏原覆盖和特殊人群文案。
- 配置并真实验证 Apple 登录、视觉 API、私有 S3、HTTPS 和相应的数据处理条款。
- 用户确认照片保留期限、删除范围和备份策略后再实现自动清理；不默认永久删除。
- 补充跨设备通知、服务监控、访问审计、速率压力测试和隐私影响评估。
