# 个人定制每日营养摄入记录 App 技术方案

## 1 方案结论

产品采用原生 iOS 优先、API First、模块化单体后端、规则优先推荐和可替换 AI 服务的技术路线。

- iOS 客户端使用 Swift 6、SwiftUI 和 Swift Concurrency，最低支持 iOS 17。
- 后端使用 TypeScript、NestJS、PostgreSQL、Redis 和 BullMQ。
- 客户端与后端通过 REST JSON API 通信，OpenAPI 3.1 是接口契约的唯一来源。
- 餐食照片先由外部多模态视觉 API 识别，再映射到可信营养数据库；模型不直接决定最终营养值。
- 动态饮食节奏、营养缺口、安全过滤和推荐排序在首版使用可测试、可审计的确定性规则。
- 架构保留 Android、Web、第三方集成和更换 AI 供应商的能力，但 MVP 不提前建设微服务平台。

这套方案优先保证 iOS 体验、迭代速度、建议可解释性和健康数据安全，同时控制 MVP 的工程复杂度。

## 2 目标和范围

### 2.1 技术目标

- 支持首次使用、Today 首页、吃前分析、拍照记录、吃后分析、Nutrition Gap、下一餐推荐和通知闭环。
- 常规页面交互即时响应，拍照后立即进入可取消的异步识别流程。
- 在网络不稳定时保留餐次草稿、照片上传任务和用户修正，恢复网络后自动重试。
- 每条推荐均可追溯到输入数据、规则版本、营养数据来源和主要解释原因。
- AI 服务、营养数据库、通知服务和对象存储均通过适配器接入，避免供应商锁定。
- API 支持未来 Android、Web 和经授权的第三方客户端。

### 2.2 MVP 不包含

- 自研餐食识别模型训练平台。
- 开放式营养聊天机器人。
- 临床营养、疾病诊断、孕期或药物相关建议。
- Kubernetes、Kafka 和大规模微服务治理。
- 社区、排行榜、积分和完整菜谱内容平台。

## 3 总体架构

系统分为 iOS App、业务 API、异步任务 Worker、关系数据库、对象存储和外部能力供应商。

1. iOS App 获取用户输入并通过签名地址上传图片。
2. API 保存餐次草稿，创建识别任务并立即返回任务编号。
3. Worker 调用视觉 API，得到结构化食物候选、烹饪方式、份量范围和置信度。
4. 营养映射模块将识别结果映射到标准食物和营养数据，生成估算区间。
5. 用户确认或修正结果后，规则引擎更新 Nutrition Gap、动态进食窗口和下一餐候选。
6. 通知调度模块根据窗口、安静时段和响应历史生成可取消任务。

后端首版采用模块化单体。API 与 Worker 可以作为两个独立进程部署，但共享领域模型和同一代码仓库。只有当识别任务量、团队边界或独立扩缩容需求明确后，才拆分服务。

## 4 技术栈

### 4.1 iOS 客户端

| 凭据 | Keychain | 只保存令牌和设备级敏感凭据 |
| 相机 | AVFoundation | 支持自定义拍照引导、清晰度检查和拍摄状态控制 |

| 能力 | 技术选择 | 说明 |

| 主数据库 | PostgreSQL | 保存用户、餐次、营养状态、规则版本和推荐记录 |
| 队列 | Redis、BullMQ | 处理图片识别、通知调度、导出和删除任务 |
| 对象存储 | S3 兼容存储 | 使用签名 URL 上传，启用服务端加密和生命周期策略 |

云平台不在代码层绑定。根据首发地区，在 AWS、Azure、Google Cloud 或符合当地网络和合规要求的云服务中选择托管产品。

## 5 API First 设计

### 5.1 基本约定

- 基础路径使用 `/v1`，破坏性变化通过新版本发布。
- 使用 JSON 和 ISO 8601 时间；服务端统一保存 UTC，客户端按用户时区显示。
- 所有写操作支持 `Idempotency-Key`，防止弱网重试产生重复餐次。
- 所有响应携带 `requestId`，便于问题追踪。
- 错误使用统一结构，至少包含 `code`、`message`、`requestId` 和可选字段错误。
- 列表接口使用游标分页，不使用不稳定的页码分页。
- OpenAPI 文件进入版本控制；CI 检查破坏性接口变化并生成 Swift 客户端。

### 5.2 首批接口

| 领域 | 代表接口 |
| --- | --- |
| 身份与资料 | `POST /v1/auth/apple`、`GET /v1/profile`、`PATCH /v1/profile` |
| 当日上下文 | `GET /v1/days/{date}`、`PUT /v1/days/{date}/context` |
| 餐次 | `POST /v1/meals`、`GET /v1/meals/{id}`、`PATCH /v1/meals/{id}` |
| 图片 | `POST /v1/uploads/presign`、`POST /v1/meals/{id}/recognition-jobs` |
| 识别任务 | `GET /v1/recognition-jobs/{id}`、`POST /v1/recognition-jobs/{id}/confirm` |
| 营养状态 | `GET /v1/days/{date}/nutrition-state` |
| 推荐 | `GET /v1/recommendations/next`、`POST /v1/recommendations/{id}/feedback` |
| 通知 | `PUT /v1/devices/{id}/push-token`、`PATCH /v1/notification-preferences` |
| 数据权利 | `POST /v1/data-exports`、`DELETE /v1/account` |

接口默认只面向第一方客户端。未来开放第三方访问时，应增加独立 OAuth Client、Scope、速率限制、审计和开发者条款，不直接复用移动端凭据。

## 6 餐食识别与营养估算

### 6.1 处理原则

视觉模型用于提出候选，不作为营养事实来源。完整流程如下：

1. 客户端压缩图片、修正方向并移除 EXIF 和定位信息。
2. 服务端完成文件类型、大小和恶意内容检查。
3. `VisionProvider` 调用外部多模态 API，要求按 JSON Schema 返回结果。
4. 返回内容包括食物候选、烹饪方式、可能的隐藏成分、份量区间和字段级置信度。
5. `FoodCatalogProvider` 将候选映射到标准食物 ID 和可信营养数据。
6. 份量估算与营养密度结合，输出区间而不是伪精确单点值。
7. 中低置信度结果必须经过用户确认；低置信度只询问一个影响最大的澄清问题。

### 6.2 外部 API 策略

首版允许使用任意合规的多模态视觉 API，但必须通过统一接口接入：

```text
VisionProvider.analyzeMeal(image, context) -> MealRecognitionResult
```

供应商选择以真实餐食评测为准，比较中文菜识别、混合菜、份量范围、结构化输出稳定性、延迟、成本、数据保留政策和部署区域。代码中不得直接散落供应商专用字段。

初期可以选择一个主供应商和一个降级供应商。超时、限流或服务不可用时，系统保留草稿并允许用户手动选择，不阻塞餐次记录。

### 6.3 营养数据

- 食物基础数据通过 `FoodCatalogProvider` 抽象。
- 首发地区和菜系确定后，选择有明确许可、版本和营养来源的数据集。
- 用户常吃餐保存为个人组合，引用标准食物并记录用户修正后的典型份量。
- 每次估算记录数据源版本、模型版本、置信度和用户修改，便于回溯与后续评测。

## 7 推荐与安全规则

推荐链路按固定顺序执行：

1. 安全与饮食约束过滤。
2. 时间窗口、睡眠和训练适配。
3. 计算高优先营养缺口。
4. 根据 Body Direction 调整能量、份量和蛋白质分布权重。
5. 根据地点、准备成本和可获得性排序。
6. 根据个人偏好、重复度和反馈调整顺序。
7. 根据数据置信度降低或提高建议强度。

规则使用 TypeScript 纯函数和版本化配置实现。每次推荐保存 `ruleVersion`、主要输入、被过滤原因、候选得分和最终解释。外部语言模型可以将已确定的原因改写为短文案，但不能绕过安全过滤、修改营养计算或生成医疗结论。

安全规则必须覆盖过敏与忌口、极端热量限制、过快减重、未成年人、高风险体重目标、进食障碍信号和特殊健康状态。命中高风险规则时停止激进个性化，显示产品边界和专业支持建议。

## 8 核心数据模型

首版包含以下主要实体：

- `User` 和 `Profile`：账号、身体基础信息、Body Direction、活动档位和时区。
- `Preference`：喜欢、不吃、过敏、忌口、准备条件和常见场景。
- `DayContext`：日期、起床、睡眠、训练、可用时间和当日状态。
- `Meal`：状态、时间、来源、份量、识别置信度和用户确认状态。
- `MealItem`：标准食物、烹饪方式、份量范围、营养范围和数据来源。
- `NutritionState`：当日目标范围、已摄入估算、缺口和优先级。
- `Recommendation`：候选、得分、解释、规则版本、置信度和采用结果。
- `RecognitionJob`：图片引用、供应商、模型版本、状态、重试和原始结构化结果。
- `NotificationPreference` 和 `NotificationJob`：权限、安静时段、计划时间和响应历史。
- `Consent` 和 `AuditEvent`：授权版本、撤回、敏感操作和数据访问记录。

营养值使用区间或期望值加误差范围，不使用浮点单点值表达虚假精度。数据库迁移必须向前兼容已发布的移动端版本。

## 9 安全与隐私

- 全链路使用 TLS；数据库、对象存储和备份启用静态加密。
- 登录令牌使用短期 Access Token 和可轮换 Refresh Token；Refresh Token 仅存 Keychain。
- 饮食照片默认私有，使用短时签名 URL，禁止公开对象地址。
- 上传前删除 EXIF 和位置信息；日志、错误追踪和分析事件不得包含照片、身体数据或完整餐次内容。
- 身份资料与分析事件使用不同标识，分析平台只接收白名单事件和必要属性。
- 提供数据导出、账号删除、照片删除和模型改进授权撤回能力。
- 核心服务使用与模型改进使用分别征得同意；默认不将用户照片用于供应商训练。
- 设置图片保留周期和删除任务，并验证对象、缩略图、缓存和备份的清理路径。
- 管理端使用最小权限、强制多因素认证并记录敏感数据访问审计。

正式上线前，需要根据首发地区完成隐私影响评估、用户协议、数据跨境和健康建议边界审查。本方案不把产品定位为医疗器械或临床决策系统。

## 10 通知与后台任务

- 本地通知用于已确定且不依赖服务端更新的时间窗口。
- 远程通知用于服务端重算、跨设备同步和已变化的推荐。
- 每个通知任务具有业务唯一键，餐次确认或窗口变化后能够立即撤销旧任务。
- 服务端统一执行安静时段、每天上限、同类节流和连续忽略降频。
- 通知负载只包含最少信息，锁屏上不展示敏感营养或身体数据。
- App 被系统挂起时不依赖后台常驻计算；服务端保存权威状态，客户端恢复后同步。

## 11 测试与质量保障

### 11.1 iOS

- 使用 Swift Testing 或 XCTest 测试领域状态、同步队列和接口模型。
- 使用 ViewInspector 或快照测试验证 Today、识别确认和错误状态。
- 使用 URLProtocol Stub 或 Mock Server 测试超时、重复请求、旧版本响应和弱网恢复。
- 使用 XCUITest 覆盖首次使用、拍照确认、修改份量和下一餐推荐主流程。

### 11.2 后端

- 使用 Vitest 或 Jest 测试领域规则、权限和 API 行为。
- 使用 Testcontainers 启动真实 PostgreSQL 和 Redis 完成集成测试。
- 对 OpenAPI 执行契约测试和破坏性变更检查。
- 对幂等、任务重试、通知取消、数据导出和账号删除执行端到端测试。

### 11.3 AI 与推荐评测

- 建立脱敏且获得授权的餐食评测集，覆盖首发菜系、混合菜、模糊照片和多人共享。
- 分别评估食物候选召回、用户修正次数、份量区间覆盖率、端到端延迟和成本。
- 为动态节奏和推荐规则准备至少二十个生活场景的黄金测试。
- 所有规则版本、模型版本和营养数据版本变更必须运行回归评测。
- AI 结果不使用单一准确率作为上线门槛，必须同时检查安全、置信度校准和用户修正成本。

## 12 仓库与工程规范

建议采用以下单仓库结构：

```text
apps/
  ios/
  api/
  worker/
packages/
  contracts/
  domain/
  rules/
infra/
docs/
tests/
```

- `contracts` 保存 OpenAPI、JSON Schema 和生成配置。
- `domain` 保存不依赖 NestJS 的领域类型与状态转换。
- `rules` 保存版本化推荐、安全和通知规则及其场景测试。
- CI 依次执行格式检查、静态检查、单元测试、集成测试、OpenAPI 兼容性检查和构建。
- 生产配置通过密钥管理服务注入，不提交 `.env`、API Key 或签名材料。

## 13 部署方案

MVP 使用三个可独立扩缩容的运行单元：

- `api`：处理同步请求和鉴权。
- `worker`：处理图片识别、通知、导出和删除任务。
- `scheduler`：生成时间窗口通知和周期性清理任务，可与 worker 同代码不同启动命令。

数据库、Redis 和对象存储使用托管服务。生产、预发布和开发环境完全隔离。数据库迁移由 CI/CD 的单独步骤执行，先迁移后发布兼容代码，避免移动端旧版本在发布期间不可用。

首版容量目标以封闭测试为准，不提前为大规模流量设计。需要重点监控 API 延迟、识别队列等待时间、AI 调用失败率、每次识别成本、营养映射失败率、通知送达和用户修正率。

## 14 分阶段实施

### 阶段 0 规则和接口原型

- 建立 OpenAPI 骨架、核心数据模型和二十个生活场景测试。
- 完成 Today 状态机、动态窗口和推荐规则的后端原型。
- 用固定图片和模拟识别结果跑通完整链路。

### 阶段 1 iOS 核心闭环

- 完成五屏首次使用、Today、Camera、Meal 和 Post meal。
- 接入主视觉 API、营养映射、三档份量确认和用户修正。
- 完成 Nutrition Gap、下一餐推荐和基础通知节流。

### 阶段 2 封闭测试

- 增加可观测性、数据导出、账号删除和运营支持工具。
- 建立餐食识别评测集，调整供应商、提示和营养映射。
- 连续运行七至十四天封闭测试，验证闭环、信任、延迟、成本和通知疲劳。

### 阶段 3 个性化和扩展

- 学习常吃餐、个人份量和提醒时机。
- 根据明确需求可选接入 HealthKit。
- 在 API 和领域模型稳定后评估 Android 客户端。

## 15 关键风险与应对

| 风险 | 应对 |
| --- | --- |
| 中文混合菜识别不稳定 | 用户确认、范围表达、个人常吃餐和供应商对比评测 |
| AI 延迟或限流 | 异步任务、超时降级、备用供应商和手动记录 |
| 营养数据授权或覆盖不足 | 数据 Provider 抽象、明确许可、首发菜系人工补齐 |
| 推荐产生不安全结果 | 确定性安全规则、版本审计、高风险降级和专业审核 |
| 通知造成疲劳 | 业务唯一键、节流、忽略降频、安静时段和一键关闭 |
| 健康数据泄露 | 数据最小化、日志白名单、私有对象、加密和删除验证 |
| API 迭代影响旧客户端 | 版本化、兼容迁移、OpenAPI 差异检查和服务端容错 |
| 外部供应商锁定 | 统一 Provider、标准领域结果、保留原始版本信息和回归集 |

## 16 立项前需要确认的决策

- 首发国家或地区、语言与主要菜系。
- 营养数据的授权来源和专业审核负责人。
- 最低 iOS 版本和支持设备范围。
